# Portflow

Bulk discharge management for the operating organization of a port site. Monorepo:
a Rust API and a React SPA.

This file is loaded in every session. Keep it short. Area-specific rules live in
`.claude/rules/` and load only when matching files are touched.

## Read what your task touches

| Before | Read |
|---|---|
| Writing or reading a spec, naming anything | `CONTEXT.md`, the group of your bounded context. Use its terms exactly. The rules its entries mention are notes: only an approved spec decides behaviour |
| Running or continuing a stage | `docs/workflow.md`, and the handover comments of the issue |
| A branch, a commit, a pull request, a spec | `docs/conventions.md` |
| Touching `apps/` or a structural choice | `docs/architecture.md` and the ADRs it names. Do not contradict an ADR; propose a new one |

## Layout

```
apps/            what is deployed (ADR 0013)
  api/           Cargo workspace: crates domain, application, infrastructure, api
  web/           React SPA (Vite, TanStack Router and Query, Tailwind, shadcn/ui)
packages/        the other workspaces (ADR 0013)
  e2e/           Playwright end-to-end and regression tests, written by the QA agent
contracts/       openapi.json, generated by the API, consumed by the web app
specs/           one folder per issue: specs/<NNN>-<slug>/ (issue number padded to three digits)
specs/_TEMPLATE/ templates of spec.md, plan.md and test-report.md
docs/            architecture, ADRs, product vision and roadmap; docs/user/ is the user documentation
scripts/         convention checks and their tests
.claude/         agents, skills, rules, the two guards, settings
.githooks/       git hooks        .github/   CI, pull request template, issue forms
```

At the root: `package.json`, `pnpm-workspace.yaml` and `turbo.json` (the workspaces),
`rust-toolchain.toml` and `.nvmrc` (pinned toolchains), `compose.yaml` and
`.env.example` (local PostgreSQL). The crates, the web app, the end-to-end suite and
`contracts/` arrive with the walking skeletons (#10, #11).

## Commands

Node from `.nvmrc` (`nvm use`), pnpm from `packageManager`, Rust from
`rust-toolchain.toml` (rustup installs it), Docker for PostgreSQL. Every command below
runs from the root of the repository, on every workspace through Turborepo.

```
pnpm install                     # dependencies of every workspace
pnpm build                       # build
pnpm lint                        # lint (Clippy, and the web linter once it exists)
pnpm format:check                # format check (rustfmt, and the web formatter)
pnpm test                        # tests; those needing PostgreSQL read DATABASE_URL
pnpm db:up                       # start the local PostgreSQL (copy .env.example to .env first)
pnpm db:down                     # stop it; the data stays in a Docker volume
pnpm <task> --filter @portflow/api   # one workspace only
```

Commands of one area are in its rule: `.claude/rules/backend.md`,
`.claude/rules/frontend.md`, `.claude/rules/testing.md`.

```
python3 scripts/conventions.py setup             # the git hooks are active
python3 scripts/conventions.py branch            # current branch name
python3 scripts/conventions.py paths             # files this branch may change
python3 scripts/conventions.py specs             # every spec and test report
python3 scripts/conventions.py spec-approved --issue N
python3 scripts/conventions.py design-approved --issue N
python3 scripts/conventions.py fr-coverage --issue N
python3 -m unittest discover -s scripts/tests    # tests of the checks themselves
```

The others (`commits`, `pr`, `test-report`) are in `docs/conventions.md`.

## Rules that always apply

1. **Human gates.** A human merges every pull request. Never merge, approve, push to
   `main`, or bypass a hook. If a gate or a guard blocks you, stop and report: do not
   look for another way to run the command.
2. **No code without an approved spec.** `spec-approved` must pass before any change
   under `apps/` or `packages/e2e/` on a `feat/` branch; when the spec has `ui_impact: yes`,
   front-end work also needs `design-approved`. An approved spec or design changes
   only through a spec or design pull request.
3. **Tests first.** Commit the failing tests before the implementation they cover.
   Never weaken an existing test to make the build pass, and never change a test you
   do not own (`packages/e2e/` is the QA agent's, the tests under `apps/` the developer's): if
   a test is wrong, say so in your report.
4. **Traceability.** Every functional requirement `FR-kkk` of issue `N` is referenced
   as `N/FR-kkk` in the name of, or a comment above, at least one test.
5. **One source of truth.** Behaviour lives in the spec, decisions in ADRs, names in
   `CONTEXT.md`, user-facing labels in the approved mock-ups, the API in
   `contracts/openapi.json`. Do not duplicate them, and never settle a business rule
   yourself: ask the human.
6. **Stay in scope.** Change only what the issue asks. Report anything else you notice
   instead of fixing it.
7. **Say what you did not verify.** Never claim a check passed if you did not run it.
8. **The frame is not yours to change.** The guards, `.claude/settings.json`, the git
   hooks, `scripts/`, the conventions workflow, the templates and the issue forms
   change only on a `chore/` branch, on request. Never edit them to get past a check.
9. **Languages.** Everything written to the repository and to GitHub is in English:
   code, specs, docs, commits, pull requests, issue comments. Two exceptions are in
   French: the labels the user sees, and `docs/user/`. Talk to the human in French.
10. **Small commits.** Commit each change on its own, as you go: a rename, a test, a
    step of the implementation. Never gather a branch into one commit or rewrite its
    history: the pull request is merged by squash. See `docs/conventions.md`.

## Workflow entry points

- `/discover`: product vision, story map, roadmap and issues (rare).
- `/spec <issue>`: interview, spec, security review, then the spec PR.
- `/design <issue>`: design brief, then the design PR once the mock-up exists.
- `/develop <issue>`: plan, code, unit and integration tests on the work branch. Does not open the PR.
- `/test <issue>`: independent end-to-end and regression tests, then the test report.
- `/doc <issue>`: user documentation, then the code PR.
- `/review <pr>`: independent code and security review of a PR, and check of its test report.

One stage per session, in this order. A bug starts with `/test`. A chore has no skill.
See `docs/workflow.md`.

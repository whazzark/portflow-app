# Architecture

A modular monolith in a monorepo. One deployable Rust binary, one React single-page
application, PostgreSQL, and file storage for generated reports. Decisions and their
reasons are in `docs/adr/`.

## What runs

| Component | Responsibility |
|---|---|
| API (Rust, Axum) | HTTP, sessions, server-sent events, background worker |
| PostgreSQL | Data, sessions, job queue |
| File storage | Generated PDF reports |
| Web app (React) | Served under the same origin as the API |

No message broker and no cache. Two ports in the domain (job queue, event publisher)
keep the door open.

## Repository layout (target)

```
apps/
  api/                       Cargo workspace
    migrations/
    crates/
      domain/                entities, value objects, errors, ports
      application/           one file per use case; queries
      infrastructure/        PostgreSQL repositories, jobs, events, mail, storage
      api/                   routes, DTOs, OpenAPI, composition root
    tests/                   HTTP integration tests
  web/                       React SPA
packages/                    workspaces that are not deployed (ADR 0013)
  contracts/                 openapi.json, generated by the API, and its TypeScript types (ADR 0016)
  design-system/             tokens, atoms, molecules, templates; Storybook; synced with Claude Design (ADR 0019)
  e2e/                       Playwright end-to-end and regression tests
  user-docs/                 user documentation, in English
specs/                       one folder per issue (docs/conventions.md)
docs/  scripts/
.claude/  .githooks/  .github/   the frame: agents, skills, rules, guards, hooks, CI
```

## Back end: hexagonal architecture with DDD

```
api  ->  application  ->  domain
infrastructure  ->  application, domain
```

`infrastructure` implements the ports of `domain` and the query traits of
`application`; nothing depends on `infrastructure` except the composition root in `api`.

The domain depends on nothing technical. The dependency rule is enforced by the
crates' `Cargo.toml`: the `domain` crate does not declare `sqlx` or `axum`, so it
cannot import them.

Bounded contexts, with the same module name in every crate:

| Context | Owns |
|---|---|
| `auth` | Credentials, sessions, the current user |
| `users` | Identity, role, access status, invitations |
| `references` | Customers, trucks, docks, warehouses and their doors |
| `discharges` | Discharge lifecycle, product lots, shifts, rotations, weighings |
| `reporting` | Report snapshots, activity log |
| `shared` | Identifiers and tiny value objects only |

Rules between contexts: reference by identifier; never write another context's data;
read it through a port.

Cross-cutting: the use case owns the transaction, receives the `CurrentUser`, writes
the activity log and schedules jobs in that same transaction, and publishes events
after commit for the real-time stream.

## Contract

The contract is the workspace `@portflow/contracts` (ADR 0016). The API generates
`packages/contracts/openapi.json` from its code (utoipa); the TypeScript types are
generated from that file into `packages/contracts/generated/schema.d.ts`. Both files
are committed, and a test fails when one differs from what would be generated: in the
API, `the_committed_contract_matches_the_code` compares `openapi.json` with the code;
in `@portflow/contracts`, a test regenerates the types from `openapi.json` and
compares them with the committed ones. CI runs them with the other tests, and they
fail locally the same way, so a contract change that the web app does not handle
breaks the build.

The web app calls the API through `openapi-fetch`, typed by those types, and reads it
with TanStack Query: one `queryOptions` per read, its key from the key factory of its
domain (ADR 0017). Each read parses the response with a Zod schema written by hand, whose
input is bound to the generated type, so the cache holds parsed values (ADR 0020).

Every error is a problem (RFC 9457) with a stable `code`, and each endpoint documents
its success response and every error it can answer (ADR 0015). A refused request body
answers `VALIDATION_FAILED` with the refused fields as JSON Pointers; the web app builds
its forms with TanStack Form and a Zod schema, and shows those errors under the fields
or in a toast (ADR 0021).

## Front end: feature slices

`app`, `routes`, `features/<context>`, `shared`, with one-way dependencies and no
import between features. Server state in TanStack Query, navigable state in the URL.
Details in `.claude/rules/frontend.md`.

Components are layered by atomic design (ADR 0012): tokens, atoms, molecules and
templates in the workspace `packages/design-system` (ADR 0019), organisms and pages in
the features. The tokens of the Tailwind theme are the only source of visual values,
and the atoms start from shadcn/ui. Storybook shows the design system, and the Portflow
design system in Claude Design, from which the mock-ups are drawn, is generated from
the package. Details in `.claude/rules/design-system.md`.

The web app is responsive and designed for touch and unreliable networks on field
screens. A native app is not planned; token-based authentication can be added later
as another adapter next to the session cookie.

## Tests

| Level | Tool | Scope | Written by |
|---|---|---|---|
| Unit: domain, use cases | `cargo test` | Rules, with in-memory fakes; no database | Developer |
| Integration: repositories | `cargo test` | Real PostgreSQL | Developer |
| Integration: HTTP | `cargo test` | The whole router, in `apps/api/tests/` | Developer |
| Unit and integration: components, features | Vitest, Testing Library, MSW | Through the real router | Developer |
| End to end and regression | Playwright, in `packages/e2e/` | User journeys from the spec | QA, without reading the implementation |

## Tooling

Cargo workspaces and pnpm workspaces, orchestrated by Turborepo through thin
`package.json` scripts. rustfmt and Clippy for Rust; Oxlint and Oxfmt for TypeScript.
CI filters by path and caches Rust builds: `.github/workflows/code.yml` runs the
`api`, `web` and `e2e` jobs only for the part a pull request touches, and its `code`
check always reports. The `e2e` job starts PostgreSQL, the API and the built web app,
and runs the Playwright suite, which also serves the built Storybook of the design
system. The `web` job keeps that Storybook as an artifact of the run; where it is
published is not decided.

Oxlint checks the import boundaries of the web app with its native rule
`no-restricted-imports`, one configuration per folder (`apps/web/.oxlintrc.json`):
its JavaScript plugins, which would run an ESLint boundaries plugin, are still alpha
in Oxlint 1.95 and are not used. Oxfmt 0.80 formats and sorts the imports
(`.oxfmtrc.json`); it is still below 1.0, so a breaking change of its output may come
with an update.

The toolchains are pinned in the repository: Rust in `rust-toolchain.toml`, Node in
`.nvmrc` and `engines`, pnpm in `packageManager`, Turborepo in `package.json`,
PostgreSQL in `compose.yaml`. A local PostgreSQL runs in Docker (`pnpm db:up`).
